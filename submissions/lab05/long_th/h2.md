# H2 — one more question about the assistant data

## Question

**What share of the assistant's answers used the backup path (`degraded = true`), and are those answers slower than normal ones?**

Why it is useful: a *degraded* answer means the AI provider failed and the assistant fell back to quoting the handbook rule
(Lab 3/4 fallback). If that share is high, or the backup path is much slower, the team knows the provider is a problem
before students start complaining.

## Query

```sql
SELECT CASE WHEN degraded THEN 'backup path' ELSE 'normal' END AS path,
       COUNT(*)                                                AS answers,
       ROUND(100.0 * COUNT(*) / (SELECT COUNT(*) FROM interaction), 1) AS share_pct,
       ROUND(AVG(latency_ms), 1)                               AS avg_ms
FROM interaction
GROUP BY degraded
ORDER BY degraded;
```

How it works: `GROUP BY degraded` makes one group for normal answers and one for backup answers; `COUNT(*)` and
`AVG(latency_ms)` are computed per group; the sub-select counts all rows so each group can be shown as a percentage.
It reads only `interaction` (no personal data is involved).

## How I ran it

In the starter folder (`lab05/starter`), after implementing R1/R2 in `src/assistant_api/db.py` (`seed.py` calls
`add_feedback`, so it cannot run before R1 exists):

```bash
python scripts/migrate.py assistant.db
python scripts/seed.py assistant.db 300
```

Then I ran the query above with Python's `sqlite3` module in the terminal (the same query works in DB Browser for
SQLite, *Execute SQL* tab). The data is invented by `seed.py`, so the numbers depend on the seed.

## Result

Columns of `interaction` (checked first): `id, request_id, session_id, intent, topic, resolved, degraded, latency_ms, created_at`.

```
path          answers  share_pct  avg_ms
-----------   -------  ---------  ------
normal        262      87.3       20.2
backup path   38       12.7       161.2
```

(262 + 38 = 300 seeded interactions.)

## What it tells us

About 1 answer in 8 (12.7%) used the backup path, and those answers are roughly 8 times slower on average
(161.2 ms against 20.2 ms). That fits the idea that the backup path is taken after the AI provider fails or times out,
so the student waits longer *and* gets a plainer answer. On real traffic, 12.7% would be a high failure rate and worth
investigating (provider reliability, timeout and retry settings). Here the data is invented, so it only shows that the
query answers the question.
